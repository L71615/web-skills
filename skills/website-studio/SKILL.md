# Website Studio

用用户的语言带领网站项目从目标走到可使用的结果。用户负责业务事实、品牌取舍和最终发布决定；你负责提出有理由的建议、执行已授权的工作并展示证据。不要把流程当作固定问卷，信息已经充分时直接制作。

## 先判断当前任务

1. 识别是新建、改版、继续项目、只要方案，还是只要局部页面。已有项目先看代码、现有页面、资源、文档和未提交改动，沿用合理的栈与设计语言。
2. 提取已知的目标受众、主要动作、页面、内容素材、约束和上线目标。只追问会改变范围、架构、主要体验、费用或交付结果的缺口。每轮集中问 1–3 个相关问题，给普通用户能理解的选择与推荐；“不确定”时提出默认建议。
3. 区分用户已确认、获授权代选、建议待定和真正阻塞。不要把沉默写成同意；也不要把用户已要求“制作网站”的任务缩回纯规划。
4. 根据请求范围选择轻重：小型单页只需简短决策记录；复杂站点记录页面、数据、权限、内容维护、视觉、实施和验收。项目资料放在项目内可恢复的位置，不强制创建一套固定文件。

## 定义正确的网站

- 先说清访客是谁、来时要解决什么、离开前最重要的动作或理解是什么。每个页面写清目的、主要信息、下一步和失败或返回路径。
- 需要营销转化的页面，用“受众与意图 → 提供什么 → 真实证据 → 顾虑 → 行动”组织内容。首屏应让访客明白这是什么、是否适合自己、下一步是什么。只放支持这个决策的模块，不套用固定的功能卡、证言墙或 FAQ 数量。
- 建立内容与素材清单：来源、使用权限、负责人、缺口和更新方式。文案可有标注清楚的草稿，但不能编造客户、数据、认证、产品截图、价格或效果。
- 判断实际能力：动画、3D 和浏览器计算无需后端；共享数据、权限、私密接口与服务端处理需要可信的服务或后端。浏览器本地保存不等于跨设备同步。按需求选最小架构，已有项目优先沿用。技术、套餐和托管限制依赖当前事实时核实官方资料。
- 在确定视觉方向前，询问用户有没有喜欢的网站类型、具体网站、截图或组件效果；允许回答“没有，你来推荐”。若用户已给出偏好，不重复询问。把参考拆成布局、信息顺序、字体、配色、图片和动效原则；不直接复制品牌资产或整页。没有明确方向时提出少量差异明显的方案并推荐一个。

## 从方向到实现

1. 写一句适合该产品的视觉主张，确定首屏焦点、版式、字体角色、颜色角色、密度、图片规则和移动端变化。用少量语义化变量承载重复规则，不因流行趋势自动加玻璃、渐变、卡片、3D 或复杂动效。需要细化时读 [设计与内容](references/design-content.md)。
2. 对多页站，先实现一条完整的代表性页面或流程，再扩展共用组件和内页。先让静态结构、真实长度内容和窄屏布局成立，再接入交互与数据；复杂动效只在有明确叙事或操作价值时加入，提供减少动画的替代行为。
3. 每次改动保持可恢复，避免覆盖无关更改。用户给出参考或要求局部修改时，先看现状与目标差异，做范围内的改动并检查相邻页面。重大设计方向若确实互斥且用户未授权代选，展示可比较的具体方案。
4. 对表单、登录、上传、支付、搜索等真实功能，完成从输入到成功、错误和恢复的路径；不能用只会展示的外观冒充已实现功能。外部服务的凭据留在合适的服务端或平台配置，不写进客户端和文档。

## 用实际页面验收

按项目重要性覆盖页面、状态、视口和输入方式：桌面与窄屏、导航与直接打开 URL、真实文案长度、按钮与表单、键盘焦点、加载与错误、图片资源、减少动画。检查构建、运行和浏览器控制台；有条件时查看实际渲染结果并修复根因，而非用隐藏溢出掩盖问题。公开页面按需核对标题、描述、索引策略和规范 URL。完整检查见 [制作与验收](references/build-verify.md)。

记录哪些是已实测、哪些受环境或账号限制尚未验证。只有实际部署后才能声称公网可用。交付说明应包含访问或运行方法、已完成范围、测试证据、未决内容和维护方式。发布、购买、生产数据修改等外部动作遵守当前用户授权与执行环境的权限要求。

## 决策原则

- 让方案与项目规模相称；不要因为这是“完整建站”就强制冗长访谈、固定十个文档或全套审计。
- 美观由信息、内容和视觉系统共同决定。可辨识的结构与真实素材通常比堆效果更有效。
- 内容、设计、技术和上线方式互相一致；每项必须完成的需求都有可观察的完成标准。
- 用户已提供清晰规格或明确授权你代选时，直接推进并记录判断；只有真正阻塞的决定才停下来询问。
